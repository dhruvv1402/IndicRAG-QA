# Demo

The deliverable demo is the CLI. `indicrag ask` runs the full pipeline —
language identification, retrieval, answerability, answer — and prints the
complete response object from PRD §9, so every field the brief requires is
visible in one place rather than summarised.

```bash
indicrag serve                             # web interface at http://127.0.0.1:8000
python scripts/run-demo.py                 # the six prepared queries, outputs saved
indicrag ask "<query>" --bm25-floor 18.08  # one query, the gate the paper recommends
indicrag ask "<query>" --gguf <path.gguf>  # generated rather than extracted answer
indicrag serve --api groq                  # web interface with a hosted model (Groq or Gemini)
```

**Hosted models.** `--api groq` or `--api gemini` answers with a hosted model
through its OpenAI-compatible endpoint, using the same prompt, parser and
refusal rules as the local model. Put `GROQ_API_KEY` or `GEMINI_API_KEY` in
`.env` (see `.env.example`; `.env` is gitignored); `--model` overrides the
default model name. The question and the retrieved passages are sent to that
provider, and the web page says so when a hosted model is selected. The
extracted-sentence answer stays available beside it for comparison.

`scripts/run-demo.py` runs the six queries PLAN §8 prepares, exactly as they
would be typed, and writes each response object to `docs/demo/`. Those files
are the fallback if the machine is slow on the day — say so if they are used.
It was run twice on 2026-09-24, start to finish, without intervention; the
second run reproduced every answer and citation of the first. Each query takes
about 51 s, nearly all of it loading the dense encoder, since `ask` has no
server mode.

Without `--gguf` the answer is **extracted**: the best-supporting sentence from
the retrieved passages, grounded by construction and needing no model. With it,
the answer is generated by the same prompt and parser the Module 4 arms use, at
roughly a minute more per query. The saved outputs are extractive.

`--bm25-floor 18.08` refuses when the BM25 top score is below the threshold
fitted on the dev split (paper §VI-H), whatever retriever supplies the evidence.
It is off by default. The demo runs with it on, because it is what the paper
recommends and the demo should show the system the paper describes.

## The six queries

| # | Query | Type | Result | BM25 top |
|---|---|---|---|---|
| 1 | How much is the annual premium of Pradhan Mantri Suraksha Bima Yojana? | English | answered | 30.5 |
| 2 | मनरेगा के तहत कितने दिन का रोजगार मिलता है? | Indic | answered | 19.3 |
| 3 | Scholarship ke liye minimum eligibility kya hai? | Code-Mixed | **refused** | 10.3 |
| 4 | सुकन्या समृद्धि खाता कितने वर्ष में परिपक्व होता है? | Indic | answered | 26.5 |
| 5 | What is the interest rate on a Kisan Credit Card loan in Nagaland? | English | answered | 20.7 |
| 6 | PMJDY ke tahat kitne bank khate khole gaye? | Code-Mixed | **refused** | 10.7 |

Retrieval finds the right scheme for all five answerable queries. What goes
wrong is the extractive reader on two, and the BM25 floor on two — once letting
a near-miss through, once refusing an answerable question. Both kinds of case
are in the demo on purpose.

**3 — the brief's own example, refused correctly.** The corpus holds 40
schemes and none is a scholarship scheme. Before the floor existed this query
was answered confidently from a pension passage. Its BM25 top score of 10.3
falls below 18.08, and the refusal is the exact PRD §9 string.

**2 — Devanagari query, a cross-script citation.** Classified Indic, answered
in Devanagari with the source's own Indian digit grouping (4,49,40,870), and the
fifth citation is `mgnrega-en#p0001` — an **English** passage retrieved for a
Devanagari query, which BM25 cannot do at any rank. Under plain RRF that
passage would be docked a full vote for the lexical retriever's silence.

**1 — right passage, wrong sentence.** Retrieval is right: the first citation is
the Suraksha Bima article. The extractive answer is its eligibility sentence,
not the premium. This is the extractive reader's limit, not retrieval's, and it
is what `--gguf` exists for.

**4 — retrieval right, the extracted sentence wrong.** Intended as a
cross-lingual case, it is answered monolingually: the Hindi article states the
21-year maturity itself, in `sukanya-hi#p0004` and `p0005`, and both are among
the five citations. The extractive reader then picks a sentence about the age
limit for opening an account. As in case 1, this is the reader's limit; query 2
is the demo's cross-script example.

**5 — a near-miss the floor lets through.** The corpus describes the Kisan
Credit Card scheme but gives no interest rate for Nagaland. The BM25 top score
of 20.7 clears the floor, because the question is about a scheme the corpus
covers, and the system answers with a description of the scheme. §VI-H
measures this directly: the floor catches every out-of-scope question and about
half of near-misses. Only a reader of the passage — the generator's own
abstention — can see that the specific fact is absent.

The retrieval list for this query also shows the defect §VII-B describes. The
first *retrieved* passage is `stand-up-india-hi#p0002` at a fused score of 0.058,
above the 0.033 plain RRF allows. BM25 returned that Hindi passage for an
English query, and script-aware fusion doubled a vote that was cast. The
extractive answer comes from the Kisan Credit Card passage, so the citations
lead with that, but the ranking underneath is wrong. Correcting the rule makes
dev-split retrieval worse overall (`evals/report-observed-votes.txt`), so it
stays.

**6 — over-abstention.** Retrieval finds Jan Dhan: the first citation is
`jan-dhan-hi#p0000`. But the query's BM25 top score is only 10.7, and the
floor refuses. This is the cost side of
the threshold, which at its dev-fitted setting refuses 61 of the 216 answerable
test questions. Without `--bm25-floor` the query is answered: "over 550 million
bank accounts".

## Hosting it publicly

The Space in `deploy/hf-space/` runs the same server on Hugging Face's free CPU
tier. `scripts/build-space.py` assembles the Space's whole content into
`build/hf-space/` (the package, the page, the paper files and the frozen corpus
with its indices, about 7 MB) and checks the copied indices against the copied
passages. The e5 encoder is downloaded into the image at build time.

1. Create a Space on huggingface.co: SDK **Docker**, hardware **CPU basic** (free).
2. Optional: in the Space's settings, add a **secret** `GROQ_API_KEY`. With it the
   page offers Groq answers beside the extracted ones; without it, extracted only.
3. Log in once: `.venv\Scripts\hf auth login` (paste a token with write access).
4. Build and upload:
   ```
   . .\scripts\dev-env.ps1
   python scripts/build-space.py
   .venv\Scripts\hf upload <user>/<space> build/hf-space . --repo-type space
   ```

Public traffic is limited per visitor (12 questions a minute, 300 a day) and
hosted-model calls to 1,000 a day in total; `INDICRAG_RATE_PER_MIN`,
`INDICRAG_RATE_PER_DAY` and `INDICRAG_API_DAILY_CAP` change them. Queries are
never logged. Every response carries a content-security policy that allows
only this origin and Google Fonts.

## What the demo does not do

- **The web interface is a local demo surface.** `indicrag serve` loads the
  system once and serves `web/`, so the Playground answers in about 0.25 s
  rather than the ~51 s `ask` spends reloading the encoder. Opened as a plain
  file, the page falls back to the six rehearsed outputs in `docs/demo/`
  (embedded by `scripts/build-web.py`). It binds to localhost and is not built
  for deployment.
- **No per-query-type threshold.** One floor serves all three query types; the
  per-type abstention rates are in `evals/report-answerability-bm25.txt`.
- **First call is slow.** The dense index and encoder load per invocation, and
  generation adds about a minute. There is no server mode; the evaluation
  harness amortises this by loading once per run, which is why `eval` exists as
  a separate command rather than a loop over `ask`.
